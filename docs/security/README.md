## Identity and secrets

- **No long-lived credentials anywhere.** GitHub Actions uses OIDC to assume `cloudcart-<env>-github-ci`. Its trust policy accepts only `repo:<owner>/<repo>:ref:refs/heads/main` and `refs/tags/v*`, so pull requests cannot assume it. Its permissions: ECR push to the three CloudCart repositories, nothing else.
- **Pods get AWS access through EKS Pod Identity**, one role per controller service account (LB controller, External Secrets, EBS CSI). IMDSv2 with hop limit 1 stops pods from borrowing the node role.
- **Database password:** generated by RDS (`manage_master_user_password`), stored in Secrets Manager, synced into the cluster by External Secrets, rotated without code changes (Reloader restarts pods). It never appears in Git, Terraform code or state, Helm values, or CI logs.
- **Kubernetes Secrets** are envelope-encrypted with a customer-managed KMS key.
- **Local development:** the Compose fallback password protects a throwaway database bound to 127.0.0.1. The kind cluster generates random passwords at creation and never writes them to disk. `.gitignore` blocks `.env`, `*.tfvars`, `secrets*.yaml`, `backend.hcl` and kubeconfigs, and Trivy's secret scanner checks every push.

### NetworkPolicy finding

On kind's default CNI (kindnet), ingress rules were enforced but
**default-deny egress was not**: a random pod could still reach the Internet.
The local cluster was switched to Calico, which enforces both directions like
the EKS VPC CNI network-policy agent. The agent is enabled in Terraform
(`enableNetworkPolicy=true` on the `vpc-cni` add-on); without it EKS accepts
NetworkPolicy objects and silently ignores them.

## Accepted risks (`.trivyignore`)

| ID | Risk | Why accepted | Mitigation / exit |
|---|---|---|---|
| AWS-0040 | EKS public API endpoint enabled | operators need kubectl without a VPN in this project | CIDR allow-list enforced by validation, IAM auth on every request. Set `eks_public_endpoint = false` once a VPN or SSM bastion exists. |

## Data

- RDS: encrypted storage, TLS enforced server-side (`rds.force_ssl=1`) and client-side (`sslmode=require`), no public access, database subnets with no Internet route, security group allows 5432 only from the EKS cluster security group.
- Terraform state: S3 with KMS (customer key), versioning, TLS-only bucket policy, public access blocked, native lock file.

## Known gaps / next steps

- All services use the RDS master user. Next: one PostgreSQL role per service, limited to its own schema (`CREATE ROLE` via a Flyway callback or a migration Job).
- No mTLS between services. A service mesh (Linkerd or Istio ambient) would add workload identity and encryption in transit inside the cluster.
- Images are not signed. Next: cosign keyless signing in CI and an admission policy (Kyverno) that only admits signed images from the CloudCart ECR repositories.
- No WAF on the ALB. Add AWS WAF managed rules and rate limiting for a public deployment.
